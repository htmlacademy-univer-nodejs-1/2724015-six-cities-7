# Как работать над проектом

## Окружение

Для удобства работы над проектом используются инструменты из **Node.js** и **npm**. Все необходимые настройки произведены. Убедитесь, что на рабочем компьютере установлен актуальный LTS релиз Node.js**. Актуальная версия **Node.js** указана в файле `package.json` в поле `node`. Затем, в терминале, перейдите в директорию с проектом и _единожды_ запустите команду:

```bash
npm install
```

Команда запустит процесс установки зависимостей проекта из **npm**.

### Сценарии

В `package.json` предопределено несколько сценариев.

#### Скомпилировать проект

```bash
npm run compile
```

Создаст директорию `dist` и скомпилирует проект.

#### Удалить скомпилированный проект

```bash
npm run clean
```

Удаляет директорию `dist`. Используется перед компиляцией.

#### Собрать проект

```bash
npm run build
```

Выполняет сборку проекта: удаляет ранее скомпилированный проект и компилирует заново.

#### Проверить линтером

```bash
npm run lint
```

Запуск проверки проекта статическим анализатором кода **ESLint**.

Линтер проверяет файлы только внутри директории `src`.

**Обратите внимание**, при запуске данной команды, ошибки выводятся в терминал.

#### Запустить ts-модуль без компиляции

```bash
npm run ts -- <Путь к модулю с ts-кодом>
```

Пакет `ts-node` позволяет выполнить TS-код в Node.js без предварительной компиляции. Используется только на этапе разработки.

#### Подготовить конфигурацию

Создайте локальный `.env` по примеру `.env-example`:

```bash
cp .env-example .env
```

Заполните обязательные переменные: `DB_URI` — строка подключения MongoDB, `PORT` — номер порта, `DB_HOST` — IP-адрес сервера базы данных, `SALT` — непустая строка со случайными символами. Замените пример соли своим значением. `.env` исключён из Git.

При запуске dotenv читает `.env`, затем convict проверяет значения. Переменные, уже установленные в окружении, имеют приоритет над `.env`. При ошибке приложение выводит сообщение через логер и завершает работу. После подключения к MongoDB в лог попадают сообщение об инициализации и номер порта.

#### Запустить проект

```bash
npm start
```

В процессе запуска проекта будет выполнен процесс «Сборки проекта» и запуска результирующего кода.

#### Запустить с удобным выводом логов

```bash
npm run start:dev
```

Собирает приложение и передаёт JSON-логи pino в pino-pretty. Обычный `npm start` выводит логи в JSON. Пока приложение только проверяет конфигурацию и сообщает об инициализации, HTTP-сервер ещё не запускается.

## Структура проекта

### Директория `src`

Исходный код проекта разделён по назначению:

- `src/cli` — команды CLI и их интерфейсы.
- `src/rest` — приложение REST API. Новые модули API размещаем в `src/rest/modules`, каждый в своей директории.
- `src/shared/libs` — общие компоненты: логер и конфигурация. Каждый компонент находится в отдельной директории вместе со своим интерфейсом и типами.
- `src/shared/container` — DI-контейнер и идентификаторы зависимостей.
- `src/shared/helpers`, `src/shared/types`, `src/shared/generators` — вспомогательные функции, общие типы и генераторы данных.
- `src/main.ts` и `src/main.cli.ts` — точки входа REST-приложения и CLI.

Файлы называем строчными буквами через дефис, классы — в PascalCase. Интерфейсы храним в файлах `*.interface.ts`, типы — в `*.type.ts`. Зависимости REST-компонентов передаём через конструктор с помощью Inversify. Регистрацию зависимостей добавляем в контейнер.

### Файл `Readme.md`

Инструкции по работе с учебным репозиторием.

### Файл `Contributing.md`

Советы и инструкции по внесению изменений в учебный репозиторий.

### Остальное

Все остальные файлы в проекте являются служебными. Пожалуйста, не удаляйте и не изменяйте их самовольно. Только если того требует задание или наставник.

#### Запустить тестовый REST API

```bash
npm run mock-server
```

Запускает JSON-server на порту 3000 с данными из `mocks/mock-server-data.json`.

#### Сгенерировать тестовые предложения

Сначала запустите тестовый REST API, затем в другом терминале выполните:

```bash
npm run compile
node dist/main.cli.js --generate 100 mocks/generated.tsv http://localhost:3000/db
```

Первый аргумент — положительное целое количество предложений, второй — путь к TSV, третий — URL объекта с массивом `offers`. Файл перезаписывается. TSV содержит заголовок и по одной строке на предложение. Сгенерированные TSV исключены из Git, кроме исходного `mocks/test.tsv`.

#### Импортировать предложения

```bash
node dist/main.cli.js --import mocks/generated.tsv
```

Читает TSV по строкам и выводит предложения в консоль. Для проверки больших файлов вывод можно перенаправить:

```bash
node dist/main.cli.js --generate 3500000 mocks/large.tsv http://localhost:3000/db
node dist/main.cli.js --import mocks/large.tsv > /dev/null
```

## Модели и сервисы MongoDB (module5-task2)

Для сценариев из `project_info.md` добавлены следующие модели:

| Entity / Model | Сервис | Сценарии и методы |
| --- | --- | --- |
| `UserEntity` / `UserModel` | `UserService` | Регистрация (`create`), поиск пользователя (`findById`, `findByEmail`), проверка email и пароля (`verifyCredentials`) |
| `OfferEntity` / `OfferModel` | `OfferService` | Создание, редактирование и удаление (`create`, `update`, `delete`), список (`find`), подробности (`findById`), премиальные предложения города (`findPremium`) |
| `CommentEntity` / `CommentModel` | `CommentService` | Добавление (`create`), последние 50 комментариев предложения (`findByOfferId`) |
| `FavoriteEntity` / `FavoriteModel` | `OfferService` | Избранное пользователя (`findFavorites`), добавление и удаление (`setFavorite`) |

DTO: `CreateUserDto`, `CreateOfferDto`, `UpdateOfferDto`, `CreateCommentDto`, `SetFavoriteDto`. Автор и вычисляемые поля не изменяются через DTO редактирования предложения. Дата комментария назначается сервером. Пользователь ссылается на предложения и комментарии через ObjectId; избранное хранится парами пользователь–предложение с уникальным индексом. Удаление предложения через сервис удаляет связанные комментарии и записи избранного.

Количество комментариев и рейтинг вычисляются агрегацией MongoDB по **всем** комментариям предложения при каждом чтении. Рейтинг — средняя оценка с округлением до одного знака после запятой. После добавления оценки следующий запрос сразу возвращает новое значение; отдельного сохранённого счётчика, который может рассинхронизироваться, нет. До первой оценки рейтинг равен `0`, количество комментариев — `0`. Ограничение в 50 комментариев применяется только к списку комментариев, а не к расчёту статистики.

Флаг `isFavorite` вычисляется для запрашивающего пользователя, у анонимного клиента он всегда `false`. Список предложений содержит не более 60 записей по умолчанию (можно передать больше), премиальный список — не более трёх. Списки отсортированы от новых к старым. Пароли хешируются scrypt с индивидуальной случайной солью; хеш не возвращается в публичных выборках и в авторе предложения или комментария.

Сервисы и подключение `Database` зарегистрированы в DI-контейнере. При запуске приложение подключается к MongoDB. На этапе module5-task2 HTTP-маршруты и работа с токенами были отложены до транспортного слоя; их реализация описана в разделе module6-task1. Отдельная модель сессии для токенной авторизации не требуется. Валидация полей моделей на этом этапе не добавляется.

### Подключение базы данных

Добавьте в `.env`:

```dotenv
DB_URI=mongodb://127.0.0.1:27017/six-cities
```

`DB_URI` — строка подключения MongoDB, включая имя базы и при необходимости учётные данные. `DB_HOST` остаётся существующей настройкой проекта; фактическое подключение использует `DB_URI`.

Для локальной базы можно выполнить:

```sh
docker run --rm --name six-cities-mongo -p 127.0.0.1:27017:27017 mongo:7
```

### Интеграционная проверка

`npm run test:integration` компилирует проект и запускает сценарии сервисов на MongoDB. Передайте `TEST_DB_URI` — адрес тестового сервера:

```sh
TEST_DB_URI=mongodb://127.0.0.1:27017 npm run test:integration
```

Тест создаёт базу со случайным именем `six_cities_test_*` и удаляет только эту базу после завершения. Проверяются регистрация и уникальность email, хеширование и проверка пароля, запрет изменения чужого предложения, пересчёт рейтинга после новых и параллельных комментариев, лимиты и сортировка списков, изоляция избранного и каскадное удаление. Без `TEST_DB_URI` интеграционный тест пропускается.

## HTTP-сервер (module6-task1)

`npm start` компилирует проект, подключает MongoDB и запускает Express на `PORT` из `.env`. `npm run start:dev` запускает его с форматированным логом. Требуются переменные `PORT`, `DB_URI`, `DB_HOST` и `SALT`, как описано выше. `SALT` также используется как секрет подписи токенов: задайте длинное случайное значение и храните его только в окружении. Изменение секрета делает ранее выданные токены недействительными.

В репозитории нет OpenAPI-файла предыдущего задания. Реализованные маршруты основаны на сценариях `project_info.md`:

| Метод | Маршрут | Назначение | Доступ |
| --- | --- | --- | --- |
| POST | `/users` | Регистрация пользователя, `CreateUserDto`, ответ `UserRdo` (201) | Анонимный |
| POST | `/auth/login` | Вход, `LoginUserDto`, данные пользователя и `token` (200) | Анонимный |
| GET | `/auth/login` | Проверка авторизации, `UserRdo` (200) | Авторизованный |
| GET | `/offers?count=60` | Список предложений, `OfferSummaryRdo[]` (200) | Любой |
| POST | `/offers` | Создание, `CreateOfferDto`, ответ `OfferRdo` (201) | Авторизованный |
| GET | `/offers/premium?city=Paris` | До трёх премиальных предложений города (200) | Любой |
| GET | `/offers/favorites` | Избранные предложения пользователя (200) | Авторизованный |
| GET | `/offers/:id` | Детальная информация, `OfferRdo` (200) | Любой |
| PATCH | `/offers/:id` | Изменение, `UpdateOfferDto`, ответ `OfferRdo` (200) | Автор предложения |
| DELETE | `/offers/:id` | Удаление предложения, пустой ответ (204) | Автор предложения |
| POST | `/offers/:id/favorite` | Добавление в избранное, ответ `OfferRdo` (200) | Авторизованный |
| DELETE | `/offers/:id/favorite` | Удаление из избранного, ответ `OfferRdo` (200) | Авторизованный |

Тела запросов передаются с `Content-Type: application/json`. Пример регистрации:

```sh
curl -X POST http://localhost:3000/users \
  -H 'Content-Type: application/json' \
  -d '{"name":"Alice","email":"alice@example.com","password":"secret123","type":"regular"}'
```

После входа передавайте токен в `Authorization: Bearer <token>`. Используются подписанные HS256 JWT со сроком действия 24 часа. Сессии на сервере не хранятся; выход выполняется удалением токена у клиента, отдельного маршрута выхода нет. Автор создаваемого предложения определяется токеном, а не телом запроса. Без токена публичные маршруты возвращают `isFavorite: false`. Некорректный или просроченный токен приводит к 401.

Response Object формируется через `class-transformer` с явным списком полей. Идентификаторы возвращаются как `id`, внутренние `_id`, `__v` и хеши паролей исключены. Детальное предложение содержит объект автора, список предложений — только краткие поля из технического задания. Маршруты комментариев в этом задании не регистрируются.

`Controller` регистрирует маршруты через `express-async-handler` и предоставляет методы ответов `ok`, `created`, `noContent`. Middleware JSON и авторизации регистрируются до контроллеров, фильтр исключений — после них. Ошибки запросов возвращают `{ "type": "HTTP_ERROR", "message": "..." }` с подходящим кодом (400/401/403/404/409/413). Неожиданные ошибки возвращают 500 и `{ "type": "SERVER_ERROR", "message": "Internal server error" }`. Подробности исключений записываются в лог и не раскрываются клиенту. Бизнес-валидация DTO отложена до следующего задания.

`TEST_DB_URI=mongodb://127.0.0.1:27017 npm run test:integration` проверяет как сервисы MongoDB, так и настоящие HTTP-запросы: регистрацию и вход, права доступа, DTO/RDO, изменение и удаление предложения, избранное, ошибочный JSON, неизвестные маршруты и ошибки асинхронных обработчиков. Каждый интеграционный тест использует отдельную временную базу и удаляет её после завершения.
